# Second-pass hiring-readiness review

## 판정

**DA 70% + AE 30%의 경력 전환 포트폴리오로 설명할 근거가 갖춰졌다.** 도메인 문제 → 지표 정의 → 분석 → 해석의 한계 → 실험/중단 기준이 DA의 중심이고, SQL·모델·계약·재현·대조 검증이 이를 뒷받침한다. 비율은 포트폴리오의 강조점이다. 이 저장소만으로 Senior DA 경력이나 프로덕션 AE 경험을 입증하지는 않는다.

이번 작업은 검증된 집계 분석을 다시 만들지 않았다. 첫 감사 이후의 원본 6개 CSV, 핵심 수치와 기존 차트를 유지하면서 사용자 단위 SQL 분석과 채용 커뮤니케이션을 보완했다.

## 주요 개선 전후

| 개선 전 | 개선 후 | 채용 가치 |
|---|---|---|
| 집계 테이블 SQL만 존재 | 독립 합성 등록/접속 로그에서 exact-day D7/D30 계산; SQL↔pandas 전 결과 대조 | 사용자 단위 join, CTE, 날짜 처리, window function을 실제 문제에 적용 |
| 기존 D30 대리지표와 표준 리텐션의 혼동 위험 | 모집단·분모·분자·관측 성숙도·UTC·지연 수신 명시, 두 지표 분리 | 지표 이름보다 비즈니스 의미를 검증하는 역량 |
| 실행 방향은 있으나 종료 기준이 추상적 | 주요 발견별 대상, 가설, KPI, 가드레일, 계속/중단/반복 규칙 | 분석 결과를 다음 의사결정으로 연결 |
| README에 상세 설명과 구현 정보가 먼저 등장 | 질문·데이터·네 가지 핵심 근거·판단·검증을 먼저 제시 | 짧은 시간 안에 프로젝트 가치 파악 |
| 운영 경력의 분석 역량 연결이 추상적 | QA, 영향도, VOC/CS, 결제 이슈, 배포 검증, 협업의 증빙 준비표 | 본인 행동과 의사결정자의 책임을 구분한 면접 준비 |
| 첫 감사의 보정 경위가 여러 문서에 분산 | 변경 원인, 놓친 테스트, 변경/유지 수치와 새 방어장치 정리 | 결론을 고치는 능력 자체가 분석 엄밀성의 증거 |

## 검증 결과와 범위

- 전체 **81개 테스트 통과**: 기존 78개 + 사용자 로그 관련 3개 테스트 메서드. 각 신규 테스트는 여러 시간 경계/계약 조건을 확인한다.
- 기존 7개 분석 스크립트와 새 사용자 코호트 분석을 파이프라인에서 실행했다.
- 노트북 **19개 Python 코드 셀**을 순서대로 실행했다. 이는 Python 실행 검증이며 Jupyter UI 렌더링 검증은 아니다. 오래된 출력은 저장하지 않는다.
- 기존 SQL 4개 결과: 2,313행, 9,476개 지표 셀 대조. 추가 사용자 코호트 SQL: 18행의 모집단/성숙 분모/접속 분자/비율을 pandas와 대조했다. 분모 0의 결측도 일치한다.
- 등록 사용자 360명, 접속 수신 레코드 5,985개를 결정적으로 재생성할 수 있다. 중복 수신은 실제 사용자/세션 수가 아니다.
- 기존 6개 원본 CSV와 기존 차트는 재실행 후 첫 감사 완료 상태와 동일하다. 기존 검증 수치도 변경되지 않았다.
- README/한국어 README 각각의 7개 핵심 값은 source-derived 문서와 일치해야 한다. 기존 생성 보고서와 신규 코호트 표도 계산 결과와 일치해야 한다.
- 문서·노트북·코드의 과장 표현을 검토했다. 기존 차트/열 이름은 호환성을 유지하되, 집계 D30의 대리지표 성격과 회복 지수의 범위를 진입 문서·캡션 맥락에서 명시했다. 지역 순위를 확정적 투자 우선순위로 사용하지 않는다.

이 검증은 계산과 문서의 일관성을 확인한다. 합성 데이터의 외적 타당성, 실제 인과효과나 업무 성과를 증명하지 않는다.

## 남은 약점: 우선순위

| 등급 | 남은 항목 | 다음 행동 |
|---|---|---|
| **지원 전 필수** | 실제 업무 사례에서 본인이 한 일과 상위 의사결정자가 정한 일이 아직 확인되지 않음 | 실제 사례 2–3개에 본인 행동·전달 증거·의사결정자·후속 검증을 채운다. 확인 전에는 성과 문장으로 사용하지 않는다. |
| **지원 전 필수** | 작성된 코드와 지표를 지원자 본인이 설명할 수 있는지는 저장소만으로 판단 불가 | D30 분모, payer union 보정, SQL 중복 제거, 인과 추론 한계를 자료 없이 설명하고 작은 쿼리를 직접 수정해 본다. |
| **추후 개선** | 관측된 공개 데이터에서 예상과 다른 결과를 탐색한 증거 부족 | 별도 작은 프로젝트 하나로 데이터 생성 가정을 모르는 상태에서 질문/분석/판단을 보여준다. |
| **추후 개선** | 비용·순기여·VOC/CS·실험 결과 없음 | 적법한 공개 데이터나 명시적 예제 범위로 한 가지 의사결정만 확장한다. 예측 모델/대시보드를 무리하게 추가하지 않는다. |
| **수용 가능한 한계** | 별도 사용자 예제가 기존 집계 데이터의 원본이 아님 | 두 모집단을 합치거나 원래 이벤트 가설을 입증한 것처럼 표현하지 않는다. |
| **수용 가능한 한계** | 합성 데이터, 작은 코호트, 시나리오 가정과 미실행 실험 | 정확성을 보여주는 예제라고 설명한다. 관측 리텐션이나 생산 환경 ROI로 일반화하지 않는다. |
| **수용 가능한 한계** | SQLite 배치 재생성; 실서비스 warehouse/orchestration/SCD 미구현 | DA 중심 경력 전환 범위에는 적절하다. 프로덕션 구축 경험으로 표현하지 않는다. |

현재 확인된 저장소의 계산 오류 때문에 지원을 막아야 하는 항목은 없다. 지원 전 필수 항목은 경력 사실 확인과 본인의 설명 가능성이다.

## 예상 면접 질문 5개와 근거 있는 답변

**1. 기존 D30과 새 D30은 무엇이 다른가요?**  
기존 값은 생성기가 만든 중첩 체크포인트 대리지표입니다. 새 값은 등록일 +30일에 접속 로그가 있는 사용자 수를, 그 날짜까지 관측이 끝난 등록 사용자 수로 나눕니다. D7에 접속하지 않고 D30에 돌아와도 포함됩니다. 두 모집단은 독립적입니다. [정의](user_retention.md)

**2. 테스트가 통과했는데 왜 PU가 잘못됐나요?**  
처음 테스트는 구조와 시나리오 기대값을 확인했지만, 고유 구매자 수가 상품별 구매자 합보다 클 수 없다는 교차 테이블 불변조건이 빠졌습니다. 1,302개 행을 보정한 뒤 payer-day 지표와 지역 해석을 다시 계산했고, JP만의 경고라는 결론을 철회했습니다. [변경 기록](validation_changes.md)

**3. 구독이 다른 상품을 잠식했다고 볼 수 있나요?**  
확정할 수 없습니다. 집계 데이터에서는 인접 상품의 payer-day당 매출 하락만 확인됩니다. 신규 구매자 구성·갱신 시점·구매자 중복 가정도 설명이 됩니다. 사용자 거래와 배정 데이터를 수집하고 총 순매출/배정 사용자 지표를 쓰는 실험을 제안합니다. [설계](decision_plan.md)

**4. SQL 결과를 어떻게 믿을 수 있나요?**  
동일 원본에 SQL과 독립 pandas 구현을 적용해 모든 수치와 결측을 대조합니다. 둘 다 같은 오류를 낼 위험을 줄이기 위해 사람이 예상 답을 정한 윤일·자정·중복·지연·미성숙 fixture도 확인합니다. 원본 계약 위반은 계산 전에 거부합니다. [테스트](../tests/test_user_retention.py)

**5. 운영 5년은 DA 업무에 어떻게 도움이 되나요?**  
업무에서 어떤 로그를 의심하고 누구에게 무엇을 확인해야 하는지, 사용자 영향과 매출 위험을 어떻게 나누어 볼지에 대한 도메인 맥락입니다. 저장소는 그 질문을 지표·SQL·검증·실험으로 바꾸는 능력을 보여줍니다. 실제 직장 사례에서는 본인이 수행한 확인·분석·보고와 리더의 결정을 구분해야 합니다. 아직 확인되지 않은 성과 수치는 답변에 넣지 않습니다. [사례 준비표](operations_to_da.md)
